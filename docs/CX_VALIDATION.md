# CX 実装の実機検証結果

検証日: 2026-09-26。対象: Radeon 8060S / Windows / Python 3.12.11 /
Torch 2.9.1+rocm7.2.1。TTSモデルBF16/GPU、codec FP32/CPU、SilentCipher無効。
独立環境でアプリをポート7865に起動し、実際のHTTP APIから検証しました。

## 結果

- `/api/status`、`/api/speak`、生成WAV配信、`/api/speak-events`: 成功。
- 5文を2巡、10回の要求、計18 WAV。全ファイルのPCM16全フレーム読み出しと非無音を確認。
- 全音声のメタデータでCXモード、GPU生成、CPU復元、透かしOFFを確認。
- 標準CPU/CUDA/auto選択、CX経路の分離、同時TTS要求の直列化等の自動テスト6件: 成功。
- JavaScript構文チェック、Git差分チェック: 成功。
- パッチ適用ツール: 実際の変更前ソースで適用・構文検査・再適用時の無変更を確認。
  未知のソースは対象ソースを書き換える前に停止することを確認。
- CXの元環境で保護対象23ファイルのSHA256は変更なし。モデル2件と参照音声の元ファイルも一致。

## API経由の所要時間

40 steps、通常話速、既定参照音声。生成時間は各要求内の音声片の合計で、
初回はモデルロードを含みます。HTTP時間には分割・応答・WAV取得も含みます。
種はランダム、OSキャッシュ未統制。試験中に利用者によるLLMへの会話入力があり、システム負荷も固定していません。
従ってこれは動作確認時の記録であり、最適条件の速度保証やCPUとの比較試験ではありません。

## メモリと未確認事項

- 生成後のプロセス常駐メモリ: 約2.66〜4.96GiB。
- プロセス最大ワーキングセット: 約6.48GiB。
- PyTorch GPU最大割当: 約3.01GiB。
- Windows空きRAM: 約0.25〜16.94GiB。後半は0.25〜0.49GiB程度まで低下。

搭載RAMは128GiB、AMDドライバーの専用GPUメモリ設定は96GiB、Windowsから見える物理RAMは約31.65GiBです。
この値はRAMの全量が消費中という意味ではなく、CPU側とGPU側への割り当ての区別です。
試験終了後、31B/Q8を実行する別のLLMプロセスの常駐メモリが約18.1GiBであることを読み取り専用で確認しました。
そのプロセスの起動時刻は音声試験の途中で、モデル読み込みと試験が重なっています。
起動引数にはGPU全層オフロード要求と `mmap+mlock` があり、GPU利用設定でもCPU側の常駐メモリが残っています。
終了後の別時点ではWindows空き約4.0GiB、LLMのprivate commit約35.6GiBでした。
commitはRAMに常駐する量とは異なるため、18.1GiBに足してRAM使用量とはしません。
時系列で全プロセスの使用量は採取していないため、空きRAM減少の原因は断定していません。
低い常駐メモリ値も、メモリ圧力による追い出しの可能性があり、省メモリ化の証拠とは扱いません。

LLMへの会話入力が重なっても音声生成は完走しましたが、31Bを含む長時間の同時会話に十分な余裕があるという結論は出していません。
試験スクリプトからはLMへの会話入力、モデルのロード／アンロード、設定変更を行っていません。
APIが返すモデル一覧だけでは、その全モデルがメモリにロード済みとは判断できません。
ブラウザー上の再生・聴感評価、長時間会話、複数ユーザー負荷、NVIDIA A6000での音声再生成は今回の試験範囲外です。

更新後は [動作確認手順](CX_TESTING.md) を実施し、31Bの量子化名・コンテキスト長・同時推論条件を記録してください。
アプリと音声実行環境を分離し、既存CPU/CUDA経路は標準モードに保持しています。
